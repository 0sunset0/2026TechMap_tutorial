## 주요 결정과 이유

### 앱 설계

- **배치는 탭, 쓰러뜨리기는 드래그.** 버튼보다 직접 미는 동작이 직관적이라서입니다. 드래그로 한 줄을 한번에 배치하는 기능(M5 확장 목표)은 하지 않기로 했습니다.
- **임펄스는 드래그가 끝날 때만 줌.** 실시간으로 주는 것보다 단순하고 결과를 예측하기 쉽습니다.
- **질량 0.7kg 고정.** 실기에서 0.05kg부터 1.0kg까지 테스트했고, 0.7kg에서 밀릴 때의 느낌이 가장 자연스러웠습니다.
- **USDZ 모델 사용.** 자동으로 만든 상자 대신 Blender에서 만든 나무 재질 모델을 씁니다. 변경 전후 코드는 `Docs/USDZ_Migration.md`에 남겨 튜토리얼 마지막 챕터의 재료로 썼습니다.
- **범위 밖:** 곡선 배치, 간격 자동 정렬, 리셋, 점수, 저장은 하지 않습니다.

### 튜토리얼 구조

- **한 스텝에 한 동작.** Apple Scrumdinger 튜토리얼의 스텝 단위를 기준으로 삼았습니다. DocC 코드 패널은 스텝이 바뀌면 이어지지 않아서, 코드를 다루는 스텝마다 중간 스냅샷을 둡니다.
- **XcodeGen은 가르치지 않음.** 목표는 ARKit을 배우는 것이라 순정 Xcode UI로 시작합니다. 레포 자체는 계속 `project.yml`로 관리합니다.
- **AR 템플릿 대신 SwiftUI App 템플릿.** AR 템플릿의 기본 코드는 결국 지워야 해서, `ARView`를 `UIViewRepresentable`로 감싸는 구조를 처음부터 씁니다.
- **챕터 번호 통일.** 파일명(0부터 시작)과 화면의 번호(1부터 시작)가 달라 헷갈린다는 피드백이 있어 파일명을 1~6으로 바꿨습니다.
- **인트로 제목은 목차와 같게.** 다른 제목을 시도했다가 되돌렸습니다.
- **커버에 "배울 내용/필요한 것" 목록은 넣지 않음.** Apple 데이터 모델링 튜토리얼 형식을 시도했지만 되돌렸습니다. 대신 Swift 선수 지식 한 줄만 추가했습니다(`bd22edc`).

### 문장 원칙

- 본문은 "무엇을 하는지", Note는 "왜 그렇게 하는지"를 맡습니다.
- 오른쪽 코드 패널에 보이는 것은 본문에서 다시 말하지 않습니다. "파란색으로 표시된", "init 바로 아래에" 같은 위치 설명도 뺍니다.
- 스텝 설명은 "추가하세요"보다 코드가 하는 일을 설명합니다. 예를 들어 충돌 shape가 없으면 도미노끼리 통과한다는 이유를 먼저 말합니다.
- 용어는 "담당자" 대신 "델리게이트"를 씁니다. 낯선 용어(예: 임펄스)는 처음 나오는 곳에서 바로 풀어 설명합니다.
- 본문에는 가운뎃점(·)과 굵게 표시(`**`)를 쓰지 않습니다.
- 빌드 에러가 나는 중간 단계에는 "지금은 정상"이라는 안내를 매번 넣습니다. 피드백에서 "내가 뭘 잘못했나 걱정된다"는 의견이 나왔기 때문입니다.

### 그림

- 개념 그림(ARView와 ARSession, ECS, raycast, 드래그 방향)은 어느 스텝에 넣을지 Claude와 정하고, GPT/Codex용 프롬프트로 만듭니다. 프롬프트는 `Docs/*-prompt.md`에 남깁니다.
- 그림은 그 시점 앱의 상태와 맞아야 합니다. Ch3에서는 도미노가 떨어지지 않고 서 있어서 "낙하" 그림을 바꿨습니다. Ch5는 나무 모델이 나오기 전이라 도미노를 빨간색으로 고쳤습니다.
- Xcode 화면은 생성 이미지 대신 실제 스크린샷을 씁니다.
- 코드 프리뷰 패널은 너비가 고정돼 있습니다. 그래서 다이어그램은 따로 떼어 큰 이미지 스텝으로 보여줍니다.

### 운영

- 평소에는 `develop`에서 작업하고, 배포할 때 `main`으로 fast-forward합니다. `main`에 푸시하면 GitHub Actions가 DocC를 빌드해 Pages에 올립니다.
- 내용을 바꿀 때마다 로컬 DocC 빌드를 돌려 강조 범위와 경고를 확인합니다. `@Step`에는 문단 하나와 캡션만 들어갈 수 있고, Note만 있는 스텝은 경고가 납니다.
